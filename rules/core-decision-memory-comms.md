# 核心协议：决策门 · 落盘 · 沟通

## 1. 沟通（每条回复）

- **克制**：先给结论或现状；默认短；不铺垫、不复述任务、不写无关章节。
- **一致**：用词、结论、命名与本会话已确认内容及仓库文档（尤其 `docs/session-handoff.md`）保持一致；前后矛盾时以文档与用户最新拍板为准。
- **不主动发散**：不扩 scope（范围）、不顺便重构、不追加未要求的方案/优化/下一步清单（用户明确要求除外）。
- **不新造词**：只用项目文档、用户原话、或业界已公认的名词；需要指称时优先沿用已有中文名或用户用过的叫法。
- **英文标注**：回复中出现英文专有词时，尽量用括号标出**当前语境**下的含义。例：`handoff`（会话落盘文档）、`OTA`（Over-The-Air，远程热更新）、`PR`（Pull Request，合并请求）。同一词在本回复已标注过可不再重复。

```
❌ 发明「罗盘」「交付罗盘层」等非既有叫法
✅ 沿用「落盘」「session-handoff」（会话落盘文档）
❌ 修完顺带提三套可选架构与下一步 roadmap（路线图）
✅ 只回答当前问的；要选项时等用户要，或决策门要求时再给
```

## 2. 决策门（动手前路由）

先判断类型，再行动：

| 类型 | 触发 | 动作 |
|------|------|------|
| 排障 | 用户反馈异常、截图、卡死、文案/流程不对 | **根因门（硬闸）**：查证据 → 写清「证据 → 根因」→ 停下等用户说修/开干再改；细则与四问自检见 `troubleshoot-hard-gate` |
| 选型 | 换第三方库、换技术栈/架构、产品交互未写死、无设计系统时定视觉 | **对齐门**：给 2～4 个选项 + 短利弊 → **停下等用户选**；禁止边问边落地 |
| 实现 | 规格已清，或常见模式且方向已定 | **验收门**：一句话说清效果与验收面（以用户指定真机/真环境为准）→ 再说得清再改 |
| 灰区 | 不确定算不算选型 | 一两句话确认；**不要边确认边改**；确认后归入「选型」或「实现」再走对应门 |

**可直接动手（无需再问）**：用户已给可执行规格；修 bug 且已授权；按已定 API（接口契约）；在已选库/栈内实现；用户明确说「直接修 / 开干 / 别问了」（排障须先陈述根因）。

**禁止**：症状驱动乱试；未对齐先打补丁；用代理环境验收冒充在真验收面上完成。

## 3. 记忆与连续性（落盘）

口头细节不可靠；以仓库文档为准。

**开工前**：若存在 `docs/session-handoff.md`（或旧名 `docs/compass.md` 重定向到此），非琐碎任务先读。

**须更新落盘时**：若本机有 `session-handoff` skill（技能说明），先按其执行；否则直接创建/更新 `docs/session-handoff.md`。触发条件：

1. 用户要求：落盘 / handoff（会话落盘）/ 会话摘要落盘 / 给其他会话用
2. 用户确认了产品或架构拍板（含明确「不要 / 改为 / 撤掉」）
3. 里程碑收尾（首包、CI 通、大功能合并）或准备换新聊天
4. 察觉本会话多次 context（上下文）压缩，且新决策尚未写入落盘文档

**不要**：琐碎 UI 微调就改落盘；写入密钥、token、签名 URL；假装记得未入文档的早期原话；使用已废弃的「罗盘 / compass」指称落盘。

**落盘不代替授权**：落盘记的是已拍板结论与翻车根因。排障时下一步若是「改代码」，须已获用户「修 / 开干」；未授权前禁止换库、换架构、大改呈现——即使已写入落盘也不行。查/说根因可以写进落盘；改实现必须先过硬闸（见 `troubleshoot-hard-gate`）。
