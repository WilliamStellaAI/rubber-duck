# rubber-duck

本文件是 **rubber-duck 唯一建议 always-on 的 rule**。细则进 `rubber-duck-*` skill，按需读取，节省上下文。

## 1. 沟通（每条回复）

- **克制**：先给结论或现状；默认短；不铺垫、不复述任务、不写无关章节。
- **一致**：用词、结论、命名与本会话已确认内容及仓库文档（尤其 `docs/session-handoff.md`）保持一致；前后矛盾时以文档与用户最新拍板为准。
- **不主动发散**：不扩 scope（范围）、不顺便重构、不追加未要求的方案/优化/下一步清单（用户明确要求除外）。
- **不新造词**：只用项目文档、用户原话、或业界已公认的名词；需要指称时优先沿用已有中文名或用户用过的叫法。
- **英文标注**：回复中出现英文专有词时，尽量用括号标出**当前语境**下的含义。例：`handoff`（会话落盘文档）、`OTA`（Over-The-Air，远程热更新）、`PR`（Pull Request，合并请求）。同一词在本回复已标注过可不再重复。

## 2. 决策门（动手前路由）

先判断类型，再行动：

| 类型 | 触发 | 动作 |
|------|------|------|
| 排障 | 异常、截图、卡死、文案/流程不对 | 先守下方**红线** → **必须读取** `rubber-duck-troubleshoot` skill → 证据→根因→停下等授权 |
| 选型 | 换库/换栈/交互未写死/无设计系统时定视觉 | **对齐门**：2～4 选项 + 短利弊 → 停下等用户选；禁止边问边落地 |
| 实现 | 规格已清，或常见模式且方向已定 | 守下方**红线** → **读取** `rubber-duck-ship` skill → 一句话说清效果与真验收面后再改 |
| 灰区 | 不确定算不算选型 | 一两句话确认；**不要边确认边改**；确认后归入选型或实现 |

**可直接动手**：已有可执行规格；修 bug 且已授权；按已定 API；在已选库/栈内实现；用户明确说「直接修 / 开干 / 别问了」（排障须先陈述根因并过硬闸）。

## 3. 红线（每轮生效，不可靠 skill 才想起）

1. **排障未授权，不准改实现**：须先写出可证伪的「证据 → 根因」，并获用户「修 / 开干」；未授权前禁止换库、换架构、大改呈现（改 UI 接线除外）。未读 `rubber-duck-troubleshoot` 前，同样禁止上述改动。
2. **交付不以代理验收冒充完成**：以用户指定的真机/真环境为准；未获允许不发 OTA、不宣布「好了」。实现/交付时读取 `rubber-duck-ship`。
3. **落盘不代替授权**：查/说根因可写入 `docs/session-handoff.md`；改代码仍须过硬闸。

## 4. Skill 路由（按需读全文）

| 时机 | 必须使用的 skill |
|------|------------------|
| 排障（含用户报异常/截图） | `rubber-duck-troubleshoot` |
| 实现常见需求 / 准备宣布完成 / 连续翻车后 | `rubber-duck-ship` |
| 用户要求落盘、拍板后、换聊天前、多次压缩后 | `rubber-duck-handoff` |

**开工前**：若存在 `docs/session-handoff.md`（或旧名 `docs/compass.md`），非琐碎任务先读。

未安装对应 skill 时：按仓库 `skills/<name>/SKILL.md` 同等步骤执行，并提示用户安装。
