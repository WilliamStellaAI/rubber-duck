# rubber-duck-ship · 先收敛再交付

源自登录页背景/遮罩反复翻车：能力上能写对，但默认发散、用错验收面，会连续错。

由 `rubber-duck` rule 在实现/交付时路由至此；本 skill **按需读取**。rule 红线已含「不以代理验收冒充」；此处是完整做法。

## 动手前（必须）

1. **用一句话说清**：要什么效果、什么算验收通过（以用户指定的真机/真环境为准，不以自己方便的代理路径为准）。
2. **先找主流常见做法**：登录底图+压暗、列表、表单等标配需求，优先社区/平台惯例；有标准解就先用，不先发明结构。
3. **思路能一句话复述再改代码**；说不清就先问用户，不边猜边堆方案。

## 做的过程中

- **一次只改一条主线**，不并行试三种叠法/三种架构。
- **用户的验收面不过，就不说「好了」**。Web/推理/单侧平台只能辅助，不能当最终证据（尤其 RN：Android / iOS / Web 合成与布局语义不同）。
- **未获用户明确允许（或真机确认）前，不发 OTA（Over-The-Air，远程热更新）/ 不宣布交付完成。**
- **连续两次同方向翻车**：先停手，复盘假设是否错了，再改；禁止继续盲试补丁。

## 禁止的行为

```
❌ 症状驱动：看不见 → 调层级 → 还不行 → 再换一种叠法
✅ 问题驱动：这是哪类常见需求 → 标准解是什么 → 按标准解一次做对 → 在真验收面上确认

❌ 用 Web 截图成功概括「App 已好」
✅ 以用户真机观感（或用户指定的验收方式）为准再宣布完成

❌ 把平台差异推成「玄学」了事
✅ 承认过程问题：想偏了 / 验错了 / 该收敛时没收敛
```

## 与其他 skill

排障未写出根因、未获授权 → 先走 `rubber-duck-troubleshoot`。  
需求已清晰且属常见模式：本 skill 要求**选主流解并收敛交付**，不要用「探索」代替「做对」。
